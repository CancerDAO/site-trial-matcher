# 现有临床匹配项目分析与新项目取舍

## 可复用经验

对成熟临床匹配项目进行只读分析后，确认以下经验直接适用于本项目：

1. **患者事实先标准化**：年龄、性别、疾病、病理、分期、分子标志物、ECOG、既往治疗、合并症与实验室值必须有稳定字段，不能从语言、文件名或医院反推患者事实。
2. **相关性与入排判断分离**：疾病、病理、分子和地域只用于排序；对本项目而言，相关性不足不能先于排除判断删除试验。
3. **确定性排除必须保守**：只有明确患者事实与明确结构化标准冲突才排除。缺失或模糊信息必须保留为 unknown。
4. **逐条证据与审计**：每个结论必须能回到条件 ID、原文、患者字段、患者值、运算符和试验值。
5. **批量与断点思想**：每个患者独立计时、独立输出；一个患者失败不应破坏其他患者结果。

## 不应继承的部分

成熟项目面向完整临床决策，因此包含疗效、风险、论文、药物机制、可及性和综合决策。本项目目标更窄，这些模块会带来不必要的运行时间、模型调用和解释复杂度，全部排除。

同样不引入：

- WHO/MCP 作为每次匹配的同步依赖；合作方数据先落本地数据库。
- A2A 或多 Agent 共识；当前采集、导入、召回、入排判断是单一顺序流程。
- 消息队列、微服务拆分、复杂权限平台和重复人工审批门禁。
- 用自由文本关键词命中直接排除患者。

## 当前架构是否过度设计

当前实现只有六个必要构件：Excel 合作方合同、导入校验、SQLite、患者标准化、全集排序、入排判断。合作状态和导入批次是满足“合作方可增可减且保留历史”的最低数据结构，不属于过度设计。FTS5 保留为后续人工检索能力，不参与默认的全集预筛门槛。

需要警惕的潜在冗余是把所有自由文本都提前结构化。Demo 只对严格解析出的年龄/ECOG做自动比较，其余保留原文，避免为了“自动化率”制造假精确。

## A2A 结论

A2A 在当前 Demo 中属于过度设计：所有步骤共享一个数据库和一份审计上下文，没有跨组织自治 Agent，也没有独立协议边界。增加 A2A 会新增鉴权、发现、超时、幂等、版本兼容和分布式追踪问题，却不改善召回或入排准确性。

只有在未来出现以下真实条件时才重新评估：多个合作公司必须在各自网络内运行独立服务；平台不能持有其全量试验数据；且需要通过统一 Agent 协议实时查询。即便如此，A2A 也只应放在合作方数据交换边界，不能替代本地入排判断合同。
